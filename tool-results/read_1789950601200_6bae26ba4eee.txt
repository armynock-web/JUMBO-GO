     5→     5→## 1. มาตรฐาน Git และแหล่งความจริง (Single Source of Truth)
     6→     6→
     7→     7→### 1.1 การ Commit
     8→     8→- **ทุกครั้งที่ทำงานเสร็จ** ต้อง commit โค้ดทันที
     9→     9→- **Commit Message** ต้องเป็นภาษาไทยหรืออังกฤษที่ชัดเจน และต้องระบุ:
    10→    10→  - สิ่งที่เปลี่ยนแปลง (What)
    11→    11→  - เหตุผลที่เปลี่ยนแปลง (Why)
    12→    12→  - ไฟล์ที่ได้รับผลกระทบ (Which files)
    13→    13→- **รูปแบบ Commit Message:**
    14→    14→  ```
    15→    15→  ประเภท: คำอธิบายสั้นๆ
    16→    16→
    17→    17→  รายละเอียดเพิ่มเติม (ถ้าจำเป็น)
    18→    18→  
    19→    19→  - แก้ไขไฟล์: file1.ts, file2.ts
    20→    20→  - เพิ่มฟีเจอร์: feature-x
    21→    21→  ```
    22→    22→
    23→    23→### 1.2 การใช้ Branch
    24→    24→- **Main Branch** = แหล่งความจริงหลัก (Production Ready)
    25→    25→- **Feature Branch** = สำหรับงานแต่ละอย่าง (feature/ชื่องาน)
    26→    26→- **ทุกงานต้องอยู่ใน branch แยก** ยกเว้นการแก้ bug เล็กๆ
    27→    27→- **ชื่อ Branch:** feature/ชื่องาน-รายละเอียด (เช่น feature/user-authentication)
    28→    28→
    29→    29→### 1.3 การ Pull Request และ Code Review
    30→    30→- **ทุก branch ต้องผ่าน Pull Request** ก่อน merge เข้า main
    31→    31→- **ต้องมีการรีวิวโค้ด** อย่างน้อย 1 คน
    32→    32→- **ต้องผ่านการทดสอบอัตโนมัติ** (Automated Tests) ก่อน merge
    33→    33→- **ต้องไม่มี conflict** ก่อน merge

    35→    35→## 2. มาตรฐานการเขียนโค้ด
    36→    36→
    37→    37→### 2.1 มาตรฐานโค้ด (Code Standards)
    38→    38→- **ต้องมีการจัดรูปแบบโค้ด** (Formatting) ที่สม่ำเสมอ
    39→    39→- **ต้องมีการตั้งชื่อตัวแปร/ฟังก์ชัน** ที่ชัดเจนและเป็นมาตรฐาน
    40→    40→- **ต้องมีการเขียนคอมเมนต์** สำหรับส่วนที่ซับซ้อน
    41→    41→- **ต้องปฏิบัติตาม Best Practices** ของภาษา/เฟรมเวิร์กที่ใช้
    42→    42→
    43→    43→### 2.2 มาตรฐานความปลอดภัย (Security Standards)
    44→    44→- **ต้องไม่มีการเก็บ Secrets/Keys** ในโค้ด (ใช้ Environment Variables)
    45→    45→- **ต้องมีการตรวจสอบ Input** จากผู้ใช้ (Input Validation)
    46→    46→- **ต้องมีการป้องกัน SQL Injection** และ XSS
    47→    47→- **ต้องมีการเข้ารหัส** ข้อมูลที่ละเอียดอ่อน (Encryption)
    48→    48→- **ต้องมีการจัดการ Error** ที่เหมาะสม (Error Handling)
    49→    49→
    50→    50→### 2.3 มาตรฐานการทดสอบ (Testing Standards)
    51→    51→- **ต้องมี Unit Tests** สำหรับฟังก์ชันสำคัญ
    52→    52→- **ต้องมี Integration Tests** สำหรับการเชื่อมต่อระบบ
    53→    53→- **ต้องมี E2E Tests** สำหรับ user flow สำคัญ
    54→    54→- **Coverage Rate** ต้องไม่ต่ำกว่า 80%
    55→    55→
    56→    56→## 3. มาตรฐานการเอกสาร (Documentation Standards)
    57→    57→
    58→    58→### 3.1 เอกสารพิมพ์เขียว (Blueprint Documentation)
    59→    59→- **ต้องมีเอกสารสถาปัตยกรรม** (Architecture Document)
    60→    60→- **ต้องมีเอกสาร API** (API Documentation)
    61→    61→- **ต้องมีเอกสารการติดตั้ง** (Installation Guide)
    62→    62→- **ต้องมีเอกสารการใช้งาน** (User Guide)
    63→    63→- **ต้องอัปเดตเอกสาร** ทุกครั้งที่มีการเปลี่ยนแปลง
    64→    64→
    65→    65→### 3.2 เอกสาร Version Control
    66→    66→- **ต้องมี CHANGELOG.md** สำหรับบันทึกการเปลี่ยนแปลง
    67→    67→- **ต้องมี VERSION.md** สำหรับบันทึกเวอร์ชั่น
    68→    68→- **ต้องมีการอัปเดตเอกสาร** ทุกครั้งที่มีการ release
    69→    69→
    70→    70→## 4. ขั้นตอนการทำงาน (Workflow)
    71→    71→
    72→    72→### 4.1 ขั้นตอนก่อนเริ่มงาน
    73→    73→1. อ่านและทำความเข้าใจเอกสารพิมพ์เขียว (Blueprint)
    74→    74→2. สร้าง branch ใหม่สำหรับงานนั้น
    75→    75→3. อัปเดต todo list สำหรับงานนั้น
    76→    76→
    77→    77→### 4.2 ขั้นตอนระหว่างทำงาน
    78→    78→1. เขียนโค้ดตามมาตรฐานที่กำหนด
    79→    79→2. เขียน tests ควบคู่กับโค้ด
    80→    80→3. commit ทุกครั้งที่ทำงานเสร็จในแต่ละส่วน
    81→    81→4. อัปเดต todo list สม่ำเสมอ
    82→    82→
    83→    83→### 4.3 ขั้นตอนหลังทำงานเสร็จ
    84→    84→1. รัน tests ทั้งหมดและตรวจสอบว่าผ่าน
    85→    85→2. อัปเดตเอกสารที่เกี่ยวข้อง
    86→    86→3. สร้าง Pull Request
    87→    87→4. รอการรีวิวและ merge
    88→    88→5. อัปเดต CHANGELOG.md และ VERSION.md

    90→    90→## 5. มาตรฐานการสื่อสารกับ AI
    91→    91→
    92→    92→### 5.1 คำสั่งพื้นฐาน
    93→    93→- **สำหรับการ commit:** "ช่วยรวบรวมโค้ดทั้งหมดพร้อมผลทดสอบ แล้วสรุป commit message ให้ฉัน จากนั้นบอกคำสั่ง git ที่ใช้ commit และ push ไปยัง repository"
    94→    94→- **สำหรับการสร้าง blueprint:** "ช่วยสร้างเอกสารพิมพ์เขียวของโปรเจ็กต์ปัจจุบัน รวมถึงสถาปัตยกรรม และ commit ไฟล์เอกสารนี้"
    95→    95→- **สำหรับการทดสอบ:** "ช่วยรัน tests ทั้งหมด และรายงานผลการทดสอบ พร้อมแก้ไขปัญหาที่พบ"
    96→    96→
    97→    97→### 5.2 คำสั่งเฉพาะเจาะจง
    98→    98→- **สำหรับงานเฉพาะ:** "ช่วย[งานที่ต้องการ] ใน branch [ชื่อ branch] พร้อมอัปเดตเอกสารที่เกี่ยวข้อง"
    99→    99→- **สำหรับการแก้ bug:** "ช่วยตรวจสอบและแก้ไข [ปัญหา] พร้อมเขียน tests สำหรับการแก้ไขนี้"

   103→   103→### 6.1 การสร้างไฟล์ ZIP/TAR
   104→   104→- **เมื่อเสร็จงาน:** สร้างไฟล์ ZIP หรือ TAR ที่รวม:

   127→   127→## 7. หลักวิศวกรรมซอฟต์แวร์ (Software Engineering Principles)
   128→   128→
   129→   129→### 7.1 SOLID Principles
   130→   130→- **Single Responsibility:** แต่ละ class/module ต้องมีความรับผิดชอบเดียว
   131→   131→- **Open/Closed:** เปิดสำหรับการขยาย ปิดสำหรับการแก้ไข
   132→   132→- **Liskov Substitution:** subclass ต้องสามารถแทนที่ superclass ได้
   133→   133→- **Interface Segregation:** แยก interface ให้เล็กและเฉพาะเจาะจง
   134→   134→- **Dependency Inversion:** พึ่งพา abstraction ไม่ใช่ concrete implementation
   135→   135→
   136→   136→### 7.2 DRY Principle (Don't Repeat Yourself)
   137→   137→- **หลีกเลี่ยงการเขียนโค้ดซ้ำ**
   138→   138→- **สร้าง reusable functions/components**
   139→   139→- **ใช้ inheritance/composition อย่างเหมาะสม**
   140→   140→
   141→   141→### 7.3 KISS Principle (Keep It Simple, Stupid)
   142→   142→- **เขียนโค้ดให้เรียบง่ายและเข้าใจง่าย**
   143→   143→- **หลีกเลี่ยงความซับซ้อนที่ไม่จำเป็น**
   144→   144→- **ตั้งชื่อตัวแปร/ฟังก์ชันให้ชัดเจน**
